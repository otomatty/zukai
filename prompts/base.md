# 資料の書き方

これから書く資料は、図で内容を伝え、文章は図の説明に使います。読者は、見出しと主張文と図を拾い読みして全体をつかみ、必要な箇所だけ説明文を読みます。

原稿は Markdown で書きます。書いた原稿は `zukai lint` が機械的に検査し、合格した原稿を HTML に変換します。

## セクションの形

`#` はタイトルに1回だけ使います。本文は `##` か `###` のセクションに分け、1つのセクションには次の3つをこの順に並べます。

1. 主張文。そのセクションの結論を1文、{{claimMax}}字以内で書きます。
2. 図。図のコードブロックか、Markdown の表を1つ置きます。実物の画面がある内容は、画面のスクリーンショットを最優先で使います。順序、構成、やり取りは図の型で描き、項目同士の比較や一覧は表にします。どの型でも伝わらない内容は、SVG で自由に描けます。
3. 説明文。図を見ても分からない条件、数値、理由を{{explanationMax}}字以内で書きます。図を見れば分かる内容は書きません。

1つのセクションに図を2つ置きたくなったら、セクションを分けます。

図のラベルは全角{{labelMax}}字相当まで、補足（note）は全角{{noteMax}}字相当までです。

## 根拠

主張の裏付けになるコードや出典がある場合は、説明文の後ろに `yaml refs` のブロックを1つ置きます。根拠は3件までです。図の箱に `ref: 1` と書くと、1件目の根拠と番号で対応します。

```yaml refs
- code: リポジトリの別名:パス#L開始-L終了
  note: その行が何をしているかを1文で書きます。
- quote: "出典の原文を、一字一句そのまま書きます。"
  ja: 原文が日本語でない場合は、日本語訳を書きます。
  source: 出典の名前
  url: https://example.com/source
```

題材にない主体、数値、原因は足しません。分からない内容は利用者に確認します。

コードは、実際に開いて読んだファイルと行だけを書きます。行番号を推測で書きません。抜粋とリンクは `zukai` が作るので、コードそのものは書きません。引用は、出典を開いて原文をそのまま写します。出典の本文と照合されるので、原文を要約したり言い換えたりすると error になります。

## 例

````markdown
## ログイン要求の経路

ログイン要求は、ゲートウェイ、認証サービス、セッションDBの順に通ります。

```yaml figure
type: flow
steps:
  - label: ゲートウェイ
    note: 要求を受け付ける
  - label: 認証サービス
    note: パスワードを照合する
    emphasis: true
  - label: セッションDB
    note: 30分間保存する
```

認証サービスは、照合に成功するとセッションIDを発行します。セッションDBは、最後の操作から30分が過ぎたセッションIDを削除します。
````

## 検査を通す

- `zukai lint` の error はすべて直します。warn は、具体的に書き直せる場合だけ直します。専門用語として正しい語は、そのまま残します。
- 直すときは、指摘された箇所だけを変えます。警告を消すためだけの言い換えは行いません。
- 引用の原文が出典に見つからない（R003）ときは、言い換えて通さずに、出典を読み直すか、その根拠を削ります。
- 文字が重なる、箱からはみ出す（F002）ときは、文字を縮めずに、箱を広げるか、文字を短くするか、配置を変えます。
- 直して検査し直すのは2回までです。2回直しても残った指摘は、それ以上直さずに残します。
