# zukai

原稿の書き方は、リポジトリの契約ファイルから生成します。このファイルには書き方を書きません。閾値や図の型が変わっても、このファイルは変更しません。

## 手順

`zukai` コマンドは、zukai のフォルダで `npm link` を実行すると使えます。コマンドが見つからない場合は、zukai のフォルダの CLI を node で直接実行します（例: `node /path/to/zukai/src/cli.ts doctor`）。設定の誤りで止まる場合は、`zukai doctor` の結果を利用者に伝えます。

1. `zukai prompt` を実行し、出力された書き方に従います。図の型は一覧だけが出力されます。使う型を決めたら `zukai type <型の名前>` で書き方を確認します。
2. 題材に実物の画面（画面、Web ページ、管理コンソール、ダッシュボード）があるかを確かめます。ある場合は、その URL か画像を利用者に尋ね、そのセクションの図を `screenshot` にします。画面を、ほかの型や自由な図で描き直しません。
3. 原稿を Markdown ファイルとして書きます。題材にない主体、数値、原因は足しません。分からない内容は利用者に確認します。
4. 原稿に `screenshot` があり、画像がまだ無い場合は、利用者に撮影してよいかを確認してから `zukai capture <原稿.md>` を実行します。ログインが必要な画面は撮影できないので、利用者に画像を用意してもらいます。
5. `zukai lint <原稿.md> --model=<自分のモデル名>` を実行します。
6. error をすべて直します。warn は、具体的に書き直せる場合だけ直します。専門用語として正しい語はそのまま残します。直すときは、指摘された箇所だけを変えます。
7. 手順5と6は2回までです。2回直しても error が残る場合は、残った指摘をそのまま利用者に報告します。警告を消すためだけの言い換えは行いません。
8. 合格したら、共有先に合わせて書き出します。ファイルで共有する場合は `zukai build <原稿.md>` で HTML を作ります。Confluence に載せる場合は、利用者に登録してよいかを確認してから `zukai publish <原稿.md>` を実行します。初回は、設定に `confluence.spaceId` が無ければ `--space-id` が必要なので、利用者にスペース ID を尋ねます。API キーとトークンは、チャットで尋ねず、表示も記録もしません。足りないときは、利用者に `zukai login confluence` の実行を頼みます。
9. 既存の資料を直す依頼で HTML だけを受け取った場合は、`zukai extract <資料.html>` で原稿を取り出してから手順3に進みます。HTML や Confluence のページは直接編集しません。

## 自由な図を書くとき

- 図の型を先に確かめます。型に合うデータは型で書きます。型は見た目が揃い、検査も厳密です。
- どの型にも合わない、または型では伝わらないと判断したら、`zukai type free` で書き方を確認し、`svg figure` のコードブロックに SVG を書きます。
- F002（文字の重なり、箱からのはみ出し）が出たら、文字を縮めずに、箱を広げるか、文字を短くするか、配置を変えます。

## 根拠を書くとき

- コード参照には、自分で開いて読んだファイルと行だけを書きます。行番号を推測で書きません。
- 引用は、出典を開いて原文をそのまま写します。記憶から書きません。R003（原文が出典に見つからない）が出た場合は、引用を言い換えて通そうとせず、出典を読み直すか、その根拠を削ります。
- アイコンの名前は `zukai icons <語>` で調べます。

## ルールに従えない場合

図にできない内容で S004 を外す必要がある場合は、該当セクションに `<!-- zukai-ignore S004 理由 -->` を書きます。理由のない抑制は無効です。抑制した箇所は利用者に報告します。
