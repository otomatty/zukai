注文管理システム 運用レポート 2026年9月

この資料は、2026年9月の注文管理システムの利用状況、応答時間、障害、費用を、開発チームと運用チームに報告します。数値は data/ の CSV を集計した値です。

今月の結果

注文作成の応答時間だけが目標に届かず、ほかの3つの指標は目標を満たしました。

指標 目標 実績 結果
成功した要求の割合 99.9%以上 99.94% 達成
注文作成が500ミリ秒以内に応答した割合 95%以上 93.8% 未達
障害の件数 1件以下 1件 達成
費用 65万円以下 62万円 達成

成功した要求の割合は、全要求496万1,500件のうち、5xx エラーにならなかった要求の割合です。障害は9月17日の1件で、復旧までに29分かかりました。

要求数の推移

9月の注文作成は41.2万件で、6か月で最も多くなりました。

注文作成は、前月から7.9%増えました。注文照会は158万件で、前月から6%増えています。注文1件あたりの照会は約3.8回で、4月の3.7回からほぼ変わっていません。

曜日と時間帯ごとの負荷

負荷が最も高いのは日曜の21時台で、平日の同じ時間帯の1.4倍です。

値は、その時刻から3時間の、1分あたりの平均の要求数です。日曜の21時台は73件、平日の21時台は平均52件でした。3時台はどの曜日も5件以下なので、DB の保守作業はこの時間帯に行います。

応答時間の目標に対する実績

500ミリ秒以内に応答した割合は、注文作成だけが目標の95%を下回りました。

注文作成は41万2,000件のうち、2万5,544件が500ミリ秒を超えました。注文作成は処理の途中で決済サービスの応答を待つため、ほかの API より応答に時間がかかります。

応答時間のばらつき

注文作成の応答時間は、中央値が277ミリ秒で、遅い要求は600ミリ秒を超えます。

各 API から40件ずつ抜き出した値です。注文作成は、4件に1件が404ミリ秒以上かかっています。注文照会と在庫照会は、最も遅い要求でも103ミリ秒以内でした。

注文が成立しなかった理由

注文の要求41万2,000件のうち、91.7%が決済まで成功しました。

成立しなかった理由で最も多いのは在庫不足で、要求の3%です。決済の時間切れは2,350件で、決済サービスが3秒以内に応答しなかった注文です。時間切れの注文は取消になり、利用者は注文をやり直す必要があります。

5xx エラーの原因

5xx エラー2,900件のうち、64%は9月17日の障害で発生しました。

DB 接続の枯渇による1,860件は、すべて9月17日の20時9分から20時38分の間に発生しました。デプロイ中の切断は、タスクの入れ替えのときに、処理中の要求が打ち切られたものです。

9月17日の障害の経過

セールの開始でタスクが6つに増え、DB 接続が上限に達して、29分間エラーが続きました。

1タスクあたりの接続の上限20本は、タスクが2つの前提で決めた値でした。タスク数の上限を6へ上げた時点で、接続の上限を見直していませんでした。2つの設定は別のリポジトリにあり、片方の変更がもう片方のレビューに現れません。

費用の内訳

9月の費用は62万円で、Aurora と Fargate の2つが全体の64%を占めます。

その他は、S3 が1.3万円、Lambda が0.6万円、SQS が0.2万円です。CloudWatch の4.9万円は、ログの取り込みが大半を占めます。ログの保存期間と出力量は、10月に見直します。

10月の対応

10月は、接続の上限の再発防止と、注文作成の応答時間の改善を優先します。

対応 目的 担当 期限
接続の上限を、タスク数の上限から計算する 9月17日の障害の再発防止 基盤チーム 10月16日
DB 接続数が上限の80%を超えたら通知する 枯渇の前に気づく 基盤チーム 10月16日
決済の時間切れを、利用者の操作なしで再試行する 注文のやり直しを減らす 注文チーム 10月30日
ログの出力量を減らす CloudWatch の費用を下げる 注文チーム 10月30日

接続の上限は、order-infra が環境変数として注文APIへ渡します。この変更で、タスク数と接続の上限を1つのリポジトリで決められます。

対応の日程

接続の上限に関する2件は10月16日までに終え、残りの2件は10月30日までに終えます。

接続の上限の変更は、次のセールが始まる10月23日より前に本番へ出します。決済の再試行は、決済サービスの担当者との確認に1週間を見込んでいます。
